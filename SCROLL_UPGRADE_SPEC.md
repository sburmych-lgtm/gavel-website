## 0 · Головне, що треба знати перед початком

**Гіпотеза власника («перший і останній кадр не співпадають, потрібен перемонтаж або непрозорий блок поверх дефекту») — спростована вимірюванням.**

Метод: усі 72 кадри зведено до 96×54 у сірому, порахувано RMSE між сусідніми кадрами й на шві.

```
шов  frame_072 → frame_001 : 3.30
середня різниця сусідніх   : 3.22
відношення шов / сусідні   : 1.02×
```

Шов на **2 %** гірший за звичайний перехід між сусідніми кадрами. Це в межах шуму компресії. Перебір усіх можливих вікон циклу (довжина ≥ 30) показав, що вікно `1 → 72` — **найкраще з усіх існуючих**; друге за якістю (`2 → 72`) вже в 1.6× гірше.

**Висновок: цикл уже закільцьований коректно. Перемонтаж не потрібен. Маскувальний блок не потрібен — він приховає симптом і зіпсує композицію.**

Те, що око читає як «кадр скаче», породжують чотири інші причини. Вони перелічені нижче за спаданням впливу. Виправляти в цьому порядку.

## 1 · [CRITICAL] Цикл крутиться приблизно в 3 рази швидше, ніж треба

### Де

`src/pages/index.astro`, блок `/* --- backdrop: scroll-driven canvas frame animation --- */`, рядок ~213:

```js
const PX_PER_CYCLE = 450; // 450px scroll = 1 full canoe stroke cycle
```

### Діагноз

450 px скролу = один повний гребок. Сторінка має 13 секцій і в зібраному вигляді набирає близько **10 000–12 000 px** висоти. Отже за один прохід сторінки веслувальник робить **приблизно 22–26 повних гребків**.

Наслідки, обидва погані:

1. Один поворот колеса миші (~100 px) зміщує кадр на 16 позицій із 72. Один флік трекпада (300–800 px) прокручує від 3/4 циклу до майже двох циклів. Око не встигає зібрати рух у безперервну дію — воно бачить серію мигтінь, і **кожен перехід через шов читається як склейка**, навіть якщо шов ідеальний.
2. Жодна людина не робить 22 гребки за час прочитання лендінгу. Ритм неправдоподібний, тому фон читається як gif, а не як зйомка.

### Урок з peachweb.io

Там документ 11 187 px, а змістовних блоків дев'ять — приблизно **1.4 екрана скролу на одну візуальну подію**. Секцію міряє тривалість скрол-скрабу, а не висота контенту. Тому їхня 3D-сцена ніколи не встигає повторитися в межах поля зору.

### Що зробити

Прив'язати цикл до висоти вьюпорта, а не до фіксованих пікселів. Замінити константу на функцію:

```js
// Один гребок = 1.35 екрана скролу. На 900px вьюпорті це 1215px,
// на 1080px — 1458px. Сторінка ~11000px → ~8 гребків за прохід.
// Це темп реального веслувальника і кожен шов зустрічається у 3 рази рідше.
const STROKE_VIEWPORTS = 1.35;
let pxPerCycle = window.innerHeight * STROKE_VIEWPORTS;
```

`pxPerCycle` перераховувати в `resize` (з дебаунсом 150 мс) і на `orientationchange`.

**Мобільний окремо.** На телефоні вьюпорт ~700–850 px, але великий палець прокручує набагато агресивніше. Ставити `STROKE_VIEWPORTS = 1.8` при `window.innerWidth < 768`.

### Критерій приймання

Проскролити сторінку від верху до низу з нормальною швидкістю читання. Порахувати гребки. Має вийти **7–9**, не 20+.

## 2 · [CRITICAL] Кадри перемикаються різко, без змішування

### Де

Той самий блок, `tick()`, рядки ~253–280.

### Діагноз

Поточна логіка:

```js
if (Math.abs(diff) > 0.04) {
  smoothFrame = ((smoothFrame + diff * 0.35) + TOTAL_FRAMES) % TOTAL_FRAMES;
  const frameIdx = Math.floor(smoothFrame) % TOTAL_FRAMES;
  if (frameIdx !== currentFrame) {
    ctx.drawImage(img, 0, 0, canvas.width, canvas.height);
```

Три проблеми в трьох рядках:

- **`Math.floor(smoothFrame)`** — дробова частина інтерполяції обчислюється, але викидається. Полотно завжди показує рівно один цілий кадр. Уся «плавність» лерпа існує тільки в числі, не на екрані.
- **`if (Math.abs(diff) > 0.04)`** — мертва зона. Коли скрол зупиняється, лерп асимптотично наближається до цілі, перетинає поріг 0.04 і **завмирає на випадковому кадрі**. Стоп-кадр посеред гребка виглядає як заїдання.
- **Рівно один `drawImage` за RAF-тік.** При різкому скролі ціль стрибає на 40+ кадрів, а полотно встигає намалювати один. При переході за якорем з навігації (`href="#pricing"`) ціль телепортується — і це вже справжня жорстка склейка, не ілюзія.

### Урок з peachweb.io

Там єдиний CSS-перехід на весь сайт — `transition: opacity 0.4s ease`, і він обслуговує саме перемикання між двома станами сцени (світлий акт / темний акт). Стани не ріжуться, вони змішуються. Той самий прийом застосовний покадрово.

### Що зробити

Малювати **два кадри з альфа-змішуванням** за дробовою частиною. Замінити тіло умови на:

```js
// без мертвої зони — лерп доводиться до кінця
smoothFrame = ((smoothFrame + diff * LERP) + TOTAL_FRAMES) % TOTAL_FRAMES;

const i0 = Math.floor(smoothFrame) % TOTAL_FRAMES;
const i1 = (i0 + 1) % TOTAL_FRAMES;
const t  = smoothFrame - Math.floor(smoothFrame);

const a = frames[i0];
const b = frames[i1];
if (a?.complete && a.naturalWidth > 0) {
  ctx.globalAlpha = 1;
  drawCover(ctx, a);                    // див. §3
  if (t > 0.01 && b?.complete && b.naturalWidth > 0) {
    ctx.globalAlpha = t;
    drawCover(ctx, b);
    ctx.globalAlpha = 1;
  }
}
```

Змінити константи:

```js
const LERP = 0.18;   // було 0.35 — з кросфейдом можна повільніше й гладше
```

Прибрати перевірку `Math.abs(diff) > 0.04` повністю. Замість неї — вихід із малювання коли рух фактично зупинився, щоб не палити батарею:

```js
if (Math.abs(diff) < 0.002 && !dirty) { rafId = requestAnimationFrame(tick); return; }
```

де `dirty` виставляється в `true` на `scroll` і `resize` і скидається після кадру.

**Обов'язково:** прибрати `alpha: false` з `getContext("2d", { alpha: false })`. З непрозорим контекстом `globalAlpha` при `drawImage` працює, але композиція з попереднім кадром дасть накопичення помилки. Використати `{ alpha: true }` і очищати перед першим шаром:

```js
const ctx = canvas.getContext("2d", { alpha: true, desynchronized: true });
```

### Критерій приймання

Прокрутити колесом на один клац і зупинитися. Веслувальник має **доїхати до кінцевої фази і зупинитися на ній плавно**, без ривка і без завмирання на півдорозі.

## 3 · [HIGH] Полотно жорстко 800×450 — фон розмитий на будь-якому екрані

### Де

`src/components/Backdrop.astro`:

```html
<canvas class="backdrop-canvas" width="800" height="450"></canvas>
```

плюс CSS:

```css
.backdrop-canvas { width: 100%; height: 100%; object-fit: cover; }
```

### Діагноз

Backing store полотна — 800×450 і ніколи не змінюється. Далі:

| Екран | Реальні пікселі | Коефіцієнт розтягу |
|---|---|---|
| 1440×900 @1× | 1600×900 (після cover) | **2.0×** |
| 1440×900 @2× (Retina) | 3200×1800 | **4.0×** |
| 2560×1440 @1× | 2560×1440 | **3.2×** |

Це головна причина «мутного фону». Гірше: **джерело `Canoe.mov` має 1024×576** — тобто кадри були свідомо зменшені *нижче* доступної роздільності. 28 % лінійної якості викинуто безкоштовно.

Другий дефект того ж блоку: `object-fit: cover` на `<canvas>` — це **другий ресемплінг поверх першого**. Спочатку `drawImage` вписує 800×450 у 800×450 backing store, потім браузер розтягує CSS-боксом. Дві інтерполяції замість однієї.

### Що зробити

**3a. Перегенерувати кадри в рідній роздільності джерела.**

Поточні 72 кадри **не відтворюються з `scripts/build-media.sh`** — скрипт створює `canoe-stroke.mp4` на 86 кадрів, а в `public/media/frames/` лежить 72 WebP. Це дрейф: кадри зроблені вручну поза пайплайном. Це треба усунути — додати крок у скрипт, щоб результат був відтворюваним:

```sh
say "scroll-driven canoe backdrop — 72-frame cycle from Canoe.mov"
mkdir -p "$OUT/frames"
# 72 кадри з 90 наявних: цикл гребка виміряно як frames 1..72 (шов 1.02× —
# перевірено RMSE-аналізом, не змінювати межі без повторного вимірювання)
ffmpeg -y -v error -i "Canoe.mov" -vf "select='lt(n\,72)',scale=1024:576:flags=lanczos" \
  -vsync 0 -c:v libwebp -quality 84 -compression_level 6 \
  "$OUT/frames/frame_%03d.webp"
```

Очікуваний розмір: ~2.2–2.6 МБ на 72 кадри проти нинішніх 848 КБ. Це прийнятно — вони вантажаться через `whenIntroIdle`, після інтро, і не конкурують з LCP.

**Якщо у клієнта є оригінал зйомки каное у 1080p або вище — використати його.** `Canoe.mov` у репозиторії 330 КБ / 1024×576 і майже напевно вже пережатий проксі. Це запитання власнику, не рішення агента.

**3b. Робити backing store під вьюпорт.**

Прибрати `width`/`height` атрибути з розмітки. Додати ресайз:

```js
const MAX_DPR = 2;
function sizeCanvas() {
  const dpr = Math.min(window.devicePixelRatio || 1, MAX_DPR);
  const w = Math.round(window.innerWidth * dpr);
  const h = Math.round(window.innerHeight * dpr);
  if (canvas.width === w && canvas.height === h) return;
  canvas.width = w;
  canvas.height = h;
  ctx.imageSmoothingEnabled = true;
  ctx.imageSmoothingQuality = "high";
  dirty = true;
}
```

**3c. Прибрати `object-fit: cover` з CSS і рахувати cover у JS.**

```js
function drawCover(ctx, img) {
  const cw = ctx.canvas.width, ch = ctx.canvas.height;
  const ir = img.naturalWidth / img.naturalHeight;
  const cr = cw / ch;
  let dw, dh;
  if (cr > ir) { dw = cw; dh = cw / ir; }   // ширший за кадр — тягнемо по ширині
  else         { dh = ch; dw = ch * ir; }
  ctx.drawImage(img, (cw - dw) / 2, (ch - dh) / 2, dw, dh);
}
```

CSS лишає тільки `width: 100%; height: 100%;` без `object-fit`.

**Бюджет пам'яті.** 72 декодованих кадри 1024×576 RGBA ≈ 170 МБ у GPU-пам'яті. Це забагато для телефона. Рішення: тримати `<img>` як є (браузер тримає стиснуті дані і декодує ліниво), **не** конвертувати в `ImageBitmap` пакетно. Якщо на слабких пристроях буде помітно — обмежити мобільну гілку 36 кадрами (кожен другий) і зменшити `MAX_DPR` до 1.5.

### Критерій приймання

Відкрити на 1440×900. Вода на фоні має мати читабельну текстуру дрібних брижів, а не суцільну градієнтну пляму.

## 4 · [HIGH] Паралакс від миші оголює краї полотна

### Де

`src/pages/index.astro`, рядки ~239–246:

```js
window.addEventListener("mousemove", (e) => {
  if (window.innerWidth < 768) return;
  const x = (e.clientX / window.innerWidth - 0.5) * 14;
  const y = (e.clientY / window.innerHeight - 0.5) * 8;
  canvas.style.transform = `translate3d(${-x}px, ${-y}px, 0)`;
}, { passive: true });
```

### Діагноз

Полотно — `position: absolute; inset: 0; width: 100%; height: 100%`. Зсув на до **±14 px по X і ±8 px по Y без жодного запасу розміру** відкриває смугу фону батька по краю екрана. На темному тлі це читається як тонка чорна рамка, що дихає за мишею. Дефект.

Другий дефект: слухач вішається безумовно, включно з планшетами і сенсорними ноутбуками, і фільтрується тільки раннім `return` **всередині** обробника. Обробник усе одно викликається на кожен рух вказівника.

Третій: `canvas.style.transform` записується синхронно в обробнику події — запис у стиль поза RAF, класичний layout thrash.

### Що зробити

```js
// вішати слухач тільки якщо пристрій справді має точний вказівник
const finePointer = window.matchMedia("(pointer: fine)");
let px = 0, py = 0, tx = 0, ty = 0;

if (finePointer.matches && !reduced.matches) {
  window.addEventListener("mousemove", (e) => {
    tx = (e.clientX / window.innerWidth - 0.5) * -14;
    ty = (e.clientY / window.innerHeight - 0.5) * -8;
  }, { passive: true });
}
// у tick(), не в обробнику:
px += (tx - px) * 0.06;
py += (ty - py) * 0.06;
canvas.style.transform = `translate3d(${px.toFixed(2)}px, ${py.toFixed(2)}px, 0)`;
```

Плюс запас розміру в CSS, щоб зсув не міг оголити край:

```css
.backdrop-canvas {
  position: absolute;
  inset: -20px;              /* запас > максимального зсуву 14px */
  width: calc(100% + 40px);
  height: calc(100% + 40px);
}
```

Демпфер `0.06` заодно перетворює різкий стрибок за мишею на інерційне ведення — це і виглядає дорожче, і прибирає нервовість.

## 5 · [MEDIUM] Постер і полотно різної роздільності — видимий стрибок якості

### Де

`src/components/Backdrop.astro` — постер 1024×576, полотно 800×450. `index.astro` ховає постер щойно завантажився перший кадр:

```js
if (poster) poster.style.display = "none";
```

### Діагноз

`display: none` — миттєве зникнення. На повільній мережі користувач бачить чіткіший постер, потім **різкий перехід на мутніше полотно**. Погіршення якості на очах — гірше, ніж якби чіткого варіанта не було зовсім.

### Що зробити

Після §3 роздільності зрівняються, але перехід усе одно має бути плавним:

```css
.backdrop-poster {
  transition: opacity 600ms cubic-bezier(0.22, 1, 0.36, 1);
}
.backdrop-poster[data-hidden] { opacity: 0; }
```

```js
// не display:none — фейд, і прибирання з потоку тільки після завершення
poster.dataset.hidden = "";
poster.addEventListener("transitionend", () => { poster.style.display = "none"; }, { once: true });
```

Ховати постер не на першому завантаженому кадрі, а коли завантажено **щонайменше 8 кадрів** — інакше кросфейд §2 не має другого шару і перші секунди все одно смикається.

## 6 · [LOW] Синтаксична неохайність у масці

### Де

`src/components/Backdrop.astro`:

```css
mask-image: linear-gradient(180deg, transparent 0%, rgba(0, 0, 0, 1) 15%, rgba(0, 0, 1) 85%, transparent 100%);
```

`rgba(0, 0, 1)` — три аргументи. Браузер за сучасною специфікацією прочитає це як `rgb(0, 0, 1)` з альфою 1, тобто **воно працює випадково**. Явна одруківка від `rgba(0, 0, 0, 1)`. Виправити в обох рядках (`mask-image` і `-webkit-mask-image`).

## 7 · Що ще варто взяти з peachweb.io — понад скрол

Це вже не баг-фікси, це підсилення. Кожен пункт незалежний, реалізовувати за рішенням власника.

### 7a · Драматургічна дуга фону замість рівного циклу [рекомендую]

**Що робить peachweb:** сторінка ділиться на два акти з інверсією паперу — світлий лавандовий верх (`#F6F5FF`) і глибокий індиго низ (`#120644`), один hue, дзеркальна світлота. Скрол — це не повтор, це подорож.

**Що це дає gavel:** зараз фон крутить один і той самий гребок від героя до футера з незмінною градацією `saturate(0.35) brightness(0.7)`. Замість цього — вести відчуття «занурення в глибину» за прогресом сторінки.

**Реалізація (ПЕРЕПИСАНО 01.09.2026, узгоджено з правилом CLAUDE.md «Animate `opacity` and `transform` only»):** НЕ анімувати `filter` на fullscreen-елементі — це і порушення зафіксованого правила, і перерахунок фільтра щокадру. Замість цього — **другий, заздалегідь заграундований оверлей** поверх бекдропа, і вести за прогресом тільки його `opacity`:

```html
<!-- у Backdrop.astro, поверх .backdrop-canvas, у тому ж маскованому контейнері -->
<div class="backdrop-grade" aria-hidden="true"></div>
```

```css
.backdrop-grade {
  position: absolute;
  inset: 0;
  pointer-events: none;
  /* преградуйований стан «глибини»: холодніше й темніше, тон від --abyss */
  background: linear-gradient(180deg, rgba(4, 10, 14, 0) 0%, rgba(4, 10, 14, 0.55) 100%);
  opacity: 0;
  will-change: opacity;
}
```

```js
// у tick(): p = прогрес сторінки 0..1 (scrollY / (scrollHeight - innerHeight))
// писати стиль лише при зміні ≥ 0.01, щоб не смикати style-recalc даремно
const target = Math.min(1, p) * 0.85;
if (Math.abs(target - lastGrade) >= 0.01) {
  gradeEl.style.opacity = target.toFixed(3);
  lastGrade = target;
}
```

Один композитний шар, анімується тільки `opacity` — правило не порушене, дроселювання через «раз на N кадрів» не потрібне. Якщо потрібна точна колірна градація (не просто затемнення) — замість градієнта покласти в `.backdrop-grade` дубль постера із запеченим у файлі `saturate/brightness` (згенерувати через `scripts/build-media.sh`, не руками).

Читається як «від відкритої води до глибини» — і це прямо римується з `--abyss` / `--deep` / `--petrol` у токенах. Прогрес сторінки вже рахується в блоці навігації (`window.scrollY > window.innerHeight * 0.6`), тобто інфраструктура є.

### 7b · Скляна панель під текстом на найтемніших ділянках [опційно]

**Що робить peachweb:** увесь текст живе на картках `backdrop-filter: blur(10px)` + напівпрозора заливка. Це те, що робить копію читабельною над складною рухомою сценою — і водночас єдиний матеріал сайту.

**Що це дає gavel:** зараз секції — це 80 % непрозорості поверх фону. Це працює, але гасить фон рівно там, де він найцікавіший. Альтернатива: секції на 100 % прозорі, а **читабельність несе локальна скляна плитка під текстовим стовпцем**.

**Застереження — це конфліктує з `docs/DECISIONS.md`:** там зафіксовано `--r: 2px` і «no rounded cards». Скляна плитка з радіусом 2 px і хайрлайном `--line` замість м'якої тіні — сумісна з цим правилом. Скляна плитка з радіусом 16 px — ні. **Не порушувати радіус.** Якщо власник не хоче скла взагалі — пункт відкинути, він не критичний.

### 7c · Пін героя замість звичайного скролу [не рекомендую]

peachweb пінить контент героя (`position: fixed`) і відпускає його по прогресу. Для gavel це **зайве**: там уже є повноекранне відео в героі, окремий інтро-фільм і фіксований фон. Ще один шар пінінгу перевантажить перше враження і зачепить LCP, який зараз навмисно не анімується (коментар у `Hero.astro` це прямо фіксує — і він правильний). Пропустити.

### 7d · Чого з peachweb НЕ брати — жодного пункту

Для протоколу, щоб код-агент не «покращив» сайт у неправильний бік:

- **Не прибирати `prefers-reduced-motion`.** peachweb не має його взагалі — це їхній дефект, а не стиль. gavel обробляє його правильно в трьох місцях (`base.css`, `Backdrop.astro`, промоушен відео). Зберегти все.
- **Не переходити на div-и замість семантики.** peachweb має 845 елементів і **нуль** `<h1>/<a>/<button>/<nav>/<section>`. gavel має правильну семантику, skip-link і доступні кнопки паузи. Це перевага gavel, не відставання.
- **Не додавати Lenis.** peachweb на ньому, але віртуальний скрол ламає нативний скрол, якорі і доступність. Поточна прив'язка до `window.scrollY` — простіша й чесніша.
- **Не додавати дубльований DOM для зміни теми.** peachweb тримає дві копії навігації і кросфейдить їх — це подвоює контент для скрінрідера.

## 8 · Порядок виконання і перевірка

1. §1 `PX_PER_CYCLE` → вьюпорт-відносний. *Найдешевша зміна з найбільшим ефектом — робити першою і показати власнику до решти.*
2. §2 кросфейд кадрів + прибрати мертву зону.
3. §4 паралакс: запас розміру + демпфер у RAF.
4. §3 перегенерувати кадри 1024×576 + ресайз backing store + `drawCover`.
5. §5 фейд постера.
6. §6 одруківка в масці.
7. §7a градація фону за прогресом — окремим комітом, щоб можна було відкотити.

### Перевірка перед комітом

```bash
npm run check        # check-facts + check-assets + check-fonts
npm run build
npm run qa
node scripts/verify-backdrop-motion.mjs
```

`scripts/verify-backdrop-motion.mjs` уже існує в репозиторії — **прочитати його перед змінами** і оновити пороги, якщо він перевіряє частоту кадрів або `PX_PER_CYCLE`.

### Ручна перевірка

| Що | Як | Очікування |
|---|---|---|
| Темп | Проскролити всю сторінку, порахувати гребки | 7–9, не 20+ |
| Шов | Зупинитися посеред гребка кілька разів | Жодного видимого стрибка |
| Зупинка | Один клац колеса, відпустити | Плавне доїзджання, без завмирання посеред фази |
| Різкий стрибок | Клікнути якір у навігації на дальню секцію | Фон не телепортується ривком |
| Краї | Водити мишею до країв екрана | Жодної темної смуги по периметру |
| Різкість | 1440×900, подивитися на воду | Видно брижі, не градієнтна пляма |
| Reduced motion | DevTools → Emulate `prefers-reduced-motion: reduce` | Полотно приховане, постер на місці, нічого не вантажиться |
| Save-Data | DevTools → throttle + `Save-Data` | Кадри не вантажаться |

### Чого не робити

- **Не додавати непрозорий блок поверх «дефекту».** Дефекту немає — див. §0. Блок закриє композицію і нічого не полагодить.
- **Не перемонтовувати `Canoe.mov`.** Цикл виміряно, він правильний.
- **Не міняти межі циклу `1..72`** без повторного RMSE-виміру. Будь-яке інше вікно гірше в 1.6× і більше.
- **Не чіпати `Hero.astro`.** Відео героя — окрема система, до фонового гребка стосунку не має, і воно є LCP-кандидатом.
- **Не міняти `--r: 2px`, `--gold`, `--caustic`** і правило «рівно одна залита золота дія на екран». Це зафіксовані клієнтські рішення в `docs/DECISIONS.md`.
